## Selected Logistic Regression over XGBoost by minimising an asymmetric business-cost metric (false negative = 5x the cost of a false positive), not by accuracy — 92 normalised cost units cheaper on validation

- **IMPLEMENTATION**: Four candidate models are declared in `get_model_factory()` at `pipeline/modeling/models.py:11-17` (LogisticRegression, DecisionTreeClassifier, RandomForestClassifier(300), XGBClassifier). The training loop fits each behind a shared `StandardScaler` `ColumnTransformer` and, for every model, searches the threshold grid `np.linspace(0.05, 0.95, 19)` that minimises `total_business_cost` on the **validation split only** (`scripts/train_models.py:143-158`). The cost function is `fn * fn_cost + fp * fp_cost` with `DEFAULT_FN_COST = 5.0` and `DEFAULT_FP_COST = 1.0` at `pipeline/modeling/threshold.py:22-23`, implemented as `total_business_cost()` at `pipeline/modeling/threshold.py:36-46`; the grid search is `find_optimal_threshold()` at `pipeline/modeling/threshold.py:91-128`. The four real validation scores, as committed in `models/production/benchmark_results.json`: **logistic_regression cost 201.0 @ threshold 0.20** (recall 0.80, precision 0.442, F1 0.5694, ROC-AUC 0.8817) — **random_forest 233.0 @ 0.25** — **xgboost 293.0 @ 0.05** (recall 0.71, precision 0.3242, F1 0.4451, ROC-AUC 0.8393) — **decision_tree 364.0 @ 0.05** (ROC-AUC 0.6554). The honest detail: on plain accuracy the ranking is completely different (XGBoost val accuracy 0.764 is in fact the *lowest* of the four) — it inverts only under the cost metric, which is the whole point of the claim.

## Implemented a tamper-evident disbursement ledger: deterministic contract codes, a SHA-256 digest over the hashed record fields verified with a constant-time compare, and a schema with UNIQUE/CHECK/FK constraints plus foreign keys enforced on every connection

- **IMPLEMENTATION**: `pipeline/storage/ledger.py`. The contract code `HDTD-YYYYMMDD-XXXX` is derived deterministically from a per-day `COUNT(*)` sequence at `:504-513`. Every row surfaced by `list_disbursements()` carries a recomputed `hash_valid` boolean (`:682-698`), which is what makes the claim tamper-*evident* rather than decorative. Schema: `loan_applications.thread_id TEXT NOT NULL UNIQUE` (`:96`), `status ... CHECK (status IN ('PENDING_REVIEW','APPROVED','REJECTED'))` (`:102-104`), `disbursements.application_id INTEGER NOT NULL UNIQUE REFERENCES loan_applications(id)` (`:112`), `contract_code TEXT NOT NULL UNIQUE` (`:113`), `status ... Replay safety: `record_disbursement()` returns the existing row for a repeated `application_id` and catches `sqlite3.IntegrityError` on a lost race (`:577-609`).

## Engineered 5 derived credit features with explicit zero-division guards that return NaN plus a machine-readable flag, feeding a 13-column serving contract declared by the model artifact itself

- **IMPLEMENTATION**: `add_derived_features()` at `pipeline/feature_engineering/features.py:22-104` produces the 5 derived columns (`DERIVED_FEATURES`, `:13-19`). Every division is guarded by a boolean mask rather than a scalar epsilon: `debt_to_income` and `loan_to_income` write NaN for rows where `income <= 0` and append the flag `income_zero_or_negative` (`:48-55`, `:59-65`); `debt_to_loan` does the same on `loan_amount <= 0` with `loan_amount_zero_or_negative` (`:69-76`); `credit_history_year_ratio` uses `np.where(age_minus_18 <= 0, 1.0, ...)` as the denominator and forces the ratio to 0 for under-18-equivalent ages, so a `max(x, 1)` guard can never be divided by zero (`:91-95`); plausibility outliers raise `employment_years_exceeds_age_minus_18` and `credit_history_exceeds_age_minus_18` (`:83-87`, `:96-98`). ## Found and fixed a Windows-only failure of the model-bundle integrity gate by running the suite on a second operating system (3 collection errors before, 164 passing after)

- **IMPLEMENTATION**: The root cause is a Git line-ending interaction, documented in the repository's own `.gitattributes:1-10` and in `docs/REPAIR-PLAN.md:11-23`. `validate_model_bundle()` re-hashes the text artefacts listed in `models/production/manifest.json`. Without `.gitattributes`, a Windows clone with `core.autocrlf=true` rewrites those files from LF to CRLF, the SHA-256 no longer matches the manifest, `load_production_model()` raises `ArtifactContractError` at `backend/predict_service.py:125`, the FastAPI lifespan at `backend/app.py:160` never finishes, and **every test module that imports the app errors during collection**. The tell-tale signature recorded at `docs/REPAIR-PLAN.md:21` is that the binary `pipeline.joblib` still matched while all four text artefacts did not — line-ending conversion, not corruption. The fix is two lines, `.gitattributes:7` and `.gitattributes:10`:
  ```
  models/production/** -text
  data/*.csv -text
  ```
  No history was rewritten; the blobs were already LF, only checkout behaviour changed.
- **FILE**: `.gitattributes`, `docs/REPAIR-PLAN.md`, `backend/predict_service.py`, `models/production/manifest.json`
- **TEST**: There is no test that asserts a `.gitattributes` — the regression protection is structural (`-text` keeps the working tree byte-identical to the committed blob) plus the whole suite now passing on Windows. `tests/test_models.py:159` `test_production_dataset_has_no_duplicate_or_overlapping_profiles` catches the same class of bug on the dataset side: it asserts `sha256(data/creditflow_dataset.csv) == meta["dataset_sha256"]`, which fails the moment a checkout rewrites the CSV.

## Known Security Issues (fix before showcasing)

These are real findings in the current tree. They are listed so the owner is not caught out by an interviewer who reads the code. **Do not put any authentication or authorization claim on the CV until S1 and S2 are fixed.**

### S1 · P0 · No authentication or authorization on the money-moving approval endpoint

`POST /predict/graph/{thread_id}/approve` is declared at `backend/app.py:531` with **no auth dependency of any kind** — no API key, no JWT, no session, no role check, no rate limit. The `approver_id` that is written into the audit record is taken **straight from the request body**: `GraphApprovalRequest.approver_id` at `backend/app.py:415`, which even defaults to the literal string `"supervisor_on_duty"`, and it is passed unvalidated into `approve_pending_application()` at `backend/app.py:580`, which stores it in `loan_applications.approver_id` (`pipeline/storage/ledger.py:651-656`). The consequence is concrete: **any anonymous caller who knows or guesses a `thread_id` can approve a pending loan and cause a `disbursements` row to be written** (`backend/app.py:651-655` -> `pipeline/storage/ledger.py:546`). Nothing in the app restricts this — no auth middleware is registered anywhere in `backend/app.py`, and the only middleware present is CORS.

- **VERIFIED**: by reading `backend/app.py:531-694` and `backend/app.py:406-417`, and by the absence of any auth import or dependency in the file. I additionally proved the endpoint is reachable with a body-supplied approver identity: `tests/test_e2e_disbursement.py:99` passes with `client.post(f"/predict/graph/{thread_id}/approve", json={"action": "approve"})` and asserts a `COMPLETED` disbursement is written — the test itself demonstrates that no credential is required.
- **Impact if shown to a reviewer**: this is the first thing a technical interviewer will find, and it negates the maturity of the ledger and approval work above.
- **Minimum fix**: a shared-secret dependency on `backend/app.py` comparing with `hmac.compare_digest`, returning 401 when unset in production; then derive `approver_id` from the authenticated identity and **never** from the body, returning 403 for non-approvers *and asserting the `disbursements` row count did not change*.

### S2 · P0 · Two evidence endpoints return customer PII and money totals to anyone
